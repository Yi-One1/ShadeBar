# 随影 ShadeBar

Windows 11 任务栏**文字与图标自适应着色**工具。实时采样任务栏自身的背景亮度，
分区域判断该用浅色还是深色，然后把结果直接写到时间、日期、系统托盘图标与
运行中指示条的画刷上——不需要你手动挑颜色。

配合 TranslucentTB 使用：任务栏透明/模糊后，时钟、日期、托盘图标在浅色壁纸上
容易糊成一片，在深色壁纸上又会发灰；随影按**当前这块背景**自动决定深浅。

> **当前版本：v1.5.1**。修复**开机后任务栏左侧图标指示条不着色**：载荷注入早于任务栏
> XAML 建完时，首次订阅只拿到时间/日期/托盘元素，随后的重放失败会让订阅永久失效。
> 现在订阅后预热 10 s、树静止才允许重放，失败按 2/5/10/30 s 退避，连续失败 3 次自动
> 重建诊断会话。其余能力与 v1.5.0 相同（配色与判定粒度解耦）。更早版本见
> [`CHANGELOG.md`](CHANGELOG.md)。
>

> `target\` 里的最新版，不会覆盖 `dist\` 里的打包 exe。

## 它能做什么

| 元素 | 是否着色 | 说明 |
|---|---|---|
| 时间（时钟文字） | ✅ | 按时钟区背景亮度自动取浅色/深色 |
| 日期 | ✅ | 与时间同区判定 |
| 系统托盘图标（网络/音量/电池/输入法…） | ✅ | 字形图标可着色；微信、QQ 等程序自绘位图图标保持原样 |
| 运行中指示条（正常态） | ✅ | 图标下方那条短横线；透明度可调 |
| 运行中指示条（选中态） | ✅ | 可与正常态分别配色；系统强调色不再覆盖 |
| 悬停高亮块 | ❌ | 尚未验证，设置项暂不开放 |
| 开始菜单 / 通知中心 / 应用内配色 | ❌ | 不动系统主题，影响面严格限制在任务栏 |

**判定粒度可切换**：默认「分区独立」——时钟区、托盘区、图标区各自采样各自判定，
遇到左深右浅的壁纸也能各段选对颜色；也可切到「全任务栏统一」，三区取平均后共用一个
明暗结论。**判定粒度只影响明暗判断方式，不影响配色**：四类内容（正常/选中指示条、
托盘字形、时间日期）在两种粒度下都各自配置「背景偏暗」与「背景偏亮」两种颜色，
正常态指示条的不透明度也独立可调。

## 工作原理

```text
任务栏自身条带（顶边下 3/5/7 px，三行取中位数）
      │  分区：时钟 93~99% / 托盘 84~93% / 图标区可调
      ▼
感知亮度 → EWMA 平滑 → 双阈值迟滞 → 二值化（亮/暗）
      ▼
浅色端 / 深色端（四类内容各自配置，默认 #FFFFFF / #000000）
      ▼
共享内存 IPC（80 字节）→ 已注入 explorer 的载荷
      ▼
CoreDispatcher 编组到 XAML UI 线程 → IVisualTreeService::SetProperty 改画刷
```

* **采样位置很关键**：必须采任务栏**自身**的条带。TranslucentTB 模糊后任务栏显示的
  颜色与它上方的壁纸并不相同，采上方会判反（真机踩过）。
* **中位数抗干扰**：三行各取行内均值，再取三行中位数，图标/文字边缘不会把判定带偏。
* **元素按 Name 定位**，不依赖符号、偏移或版本号：`TimeInnerTextBlock`、
  `DateInnerTextBlock`、`RunningIndicator`，托盘字形取 `AdaptiveTextBlock` 下
  名为 `Base` 的 `InnerTextBlock`（`Underlay` / `AccentOverlay` 是透明或强调覆盖层）。
* **指示条两态可分别配色**：正常态写元素 `Fill`（所有正常态共用同一个画刷）；
  选中态 `Fill` 被 VisualState 插了更高优先级的槽，改为直接改 `Fill` 指向的画刷
  `Color`，必要时逐层染色。每条写完都会**回读**校验，避免"返回 S_OK 但屏幕没变"。
* **状态切换与新窗口都会重新扫一遍**：正常态↔选中态不产生元素 Add 事件，
  `OnElementStateChanged` 对指示条也不触发；载荷在 XAML UI 线程每 250 ms（空闲 1 s）
  只读 `ActualWidth` 探测状态变化，变化即置脏并置急，下一拍应用（实测 0.14–0.48 s）；
  运行中新开的窗口由树变化事件接住。
* **开机能自愈**：开机时任务栏 XAML 往往尚未建完，载荷订阅只能拿到部分元素。
  重放因此改为订阅后预热 10 s、树静止 2 s 才允许；重放失败按 2/5/10/30 s 退避，
  连续失败 3 次自动释放并重建诊断会话，不再需要手动重启资源管理器。

细节与全部实测数据见 [`docs/03-recolor-mechanism.md`](docs/03-recolor-mechanism.md)。

## 系统要求

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 11（已在 26H2 Build 26300.9711 实测）；Windows 10 未验证 |
| 架构 | x86_64 |
| 运行库 | **无需安装 VC++ 运行库**（静态 CRT） |
| 权限 | 普通用户（Medium IL），`asInvoker`，**全生命周期 UAC = 0** |
| 网络 | 完全离线，无任何出站连接 |
| 体积 | 单 exe **674 KB**（690176 B；载荷 DLL 内嵌，运行时释放到 `%LOCALAPPDATA%\ShadeBar\`） |
| 常驻内存 | 托盘常驻（未打开过设置）**约 15 MB 工作集 / 4 MB 私有**；打开过设置页后收进托盘约 **8–12 MB 工作集**（NFR-02 要求 ≤ 20 MB）。注意：绘制过一帧后私有提交约 41 MB 不再归还，见 §内存口径 |
| CPU | 托盘常驻 **0.05%**（NFR-03 要求 ≤ 0.1%） |

## 与其它工具共存

* **TranslucentTB**：可共存。它的 TAP 常驻不影响随影抢到诊断席位（已实测），
  透明/模糊照常生效，随影只改元素颜色。
* **CTM 工具的同类开关**：会互相抢同一个 `TextBlock`。两者同时开启时颜色会打架，
  建议只留一个。随影不检测也不改动其它工具的设置。

## 使用

| 命令 | 行为 |
|---|---|
| 双击 / 无参数 | 单实例常驻托盘 + 采样线程 + 着色；连续双击进程数恒为 1 |
| 右键托盘图标 | 打开设置 / 开机自启动 / 版本号（只读）/ 退出 |
| `--ui` | 直接打开设置窗口 |
| `--version` | 打印 `随影 ShadeBar v1.5.1` |
| `--help` | 打印用法 |

设置页共 **28 项可见设置**（配置里保留 49 项编号，未落地 / 无视觉表现的项从 UI
收起但值不丢），采用 **720×560 四页签**布局：任务栏（实时预览 + 图标 / 托盘 / 时钟
三区 + 判定粒度 + 分区配色矩阵 + 指示条不透明度）、采样（采样带 + 间隔 / 平滑 /
区域微调）、托盘（单击 / 双击行为 + 关闭行为 + 启动 + 语言）、诊断（实时判定 +
日志级别 + 版本 + 导出诊断包）。底部固定操作栏提供恢复默认
（二次确认）、导入配置、导出配置、关于，配置导入导出写
`%LOCALAPPDATA%\ShadeBar\config-export.json`，不弹文件对话框。诊断包写
`%LOCALAPPDATA%\ShadeBar\diagnostics\shadebar-diag-<时间戳>.zip`，导出成功后在窗口
底部提示完整路径。中英双语即时切换、无「应用」按钮、改动同拍生效并落盘到
`%LOCALAPPDATA%\ShadeBar\config.json`。

开机自启走 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`：不弹 UAC、
不生成额外文件，可在任务管理器「启动」页停用。

## 构建

需要 Rust 1.99+（`rust-toolchain.toml` 锁定）、Visual Studio 2022 Build Tools 的
「Desktop development with C++」工作负载、Windows 11 SDK。

```bash
# 1) 先编 C++ 载荷（Rust 编译期会把 DLL 内嵌进 exe）
cd payload && bash build.sh && cd ..

# 2) 再编宿主
cargo build --release

# 3) 产物
target/x86_64-pc-windows-msvc/release/shadebar-app.exe
```

**顺序不能反**：`crates/shadebar-app/build.rs` 会读取 `payload/build/ShadeBarTap.dll`
并计算内容指纹，指纹进入载荷文件名（`ShadeBarTap_v1.5.1_<hash>.dll`）。
这样内容一变文件名就变，explorer 里不会因为「同名模块已加载」而静默跑旧代码。

版本号只有 `Cargo.toml` 的 `[workspace.package] version` 一个来源，
`文件名 / 关于页 / exe 属性` 三处不可能漂移。

## 已知限制

1. **需要注入 explorer**：这是元素级着色的唯一可行路径（与 CTM 工具同构）。
   写错会让任务栏重启——不会损坏系统，重启资源管理器即恢复；随影在订阅失败时
   会立刻收手，不做任何后续树操作。
2. **可能被杀软 / SmartScreen 标记**：注入行为天然敏感。若被拦截，`payload.log`
   会记录 `远程 LoadLibraryW 失败`，任务栏恢复系统默认外观，不会卡死。
3. **Windows 大版本更新后可能失效**：元素按 Name 定位，比重定位偏移稳，但微软仍可能
   改名。失效表现是「颜色不再变化」，不会崩溃。
4. ~~状态条选中态暂不由随影决定~~ → **v1.1.3 已支持**。做法是改画刷自身的 `Color`
   而不是元素的 `Fill`，因此不受视觉状态优先级影响。
5. **第三方托盘图标不改色**：位图无法单色化，硬染会丢掉图标本身的辨识度。
6. **多显示器**：1.x 只处理含任务栏的主屏。
7. **历史记录**：v1.0.0 曾判定「任务栏改色不可用」。被证伪的是当时的两条自制路线
   （叶函数 `E9` 近跳转、`OnApplyTemplate` 期间走查 XAML），共同错误是在任务栏构建期
   重入并跨时点持有瞬态指针。v1.1 改用官方 `IXamlDiagnostics` + `IVisualTreeService`
   在 XAML UI 线程改画刷，已跑通；旧结论作废，过程与踩坑记录见
   [`docs/03-recolor-mechanism.md`](docs/03-recolor-mechanism.md) 与 `docs/spike-report.md`。
